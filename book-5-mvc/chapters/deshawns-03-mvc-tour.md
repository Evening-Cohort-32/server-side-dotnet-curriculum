# How MVC Renders a Page
In this exercise we will follow a single request through an MVC app, from the URL in the browser to the HTML that comes back. There's very little code to write here. Depending on how you like to work, you will read this carefully now, or skim it and come back later. Either way, return to it after you've built a few pages, because each piece will make more sense once you've used it.

## Server-side rendering
So far in this course, the HTML that appears in your browser has mostly been generated by JavaScript _in your browser_. Your React apps start with a nearly empty `index.html`, and the JavaScript builds (or _renders_) the rest of the page from JSX and the JSON data it fetches from an API.

Server-side rendering takes a different approach. Instead of building the HTML with JavaScript on the front end, the server generates the HTML before sending a response to the browser. The server is responsible both for managing the data and for creating the UI. What it sends back is a fully-formed web page, ready to be painted in the browser window.

You can see this for yourself. Start the app, then right-click anywhere on the Welcome page and choose **View Page Source**. Every bit of that HTML, including the "Welcome" heading, came from the server. Compare that to what you'd see if you viewed the source of one of your React apps: a `<div id="root"></div>` and a few `<script>` tags.

## Model, View, Controller
MVC stands for Model, View, Controller. Models and controllers do mostly the same jobs they did when you were building web APIs. Models are C# representations of your database entities, and controller methods are still handlers for HTTP requests. The difference is that instead of sending JSON responses to the client, the handlers return HTML responses that are built with _views_.

Let's follow the request for the Welcome page through each of those pieces.

## Step 1: The route
Open `Program.cs`. Near the top, you'll find:
``` csharp
builder.Services.AddControllersWithViews();
```
This tells ASP.NET that the app will use controllers, and that those controllers will return views. Near the bottom, you'll find this:
``` csharp
app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}")
    .WithStaticAssets();
```
This is how ASP.NET decides which controller method should handle a request. In the context of ASP.NET, each public method in a controller is called an **action**. Instead of putting a `Route` attribute on every controller like you did in Bianca's Bike Shop, an MVC app usually defines one _pattern_ for all of them, and ASP.NET reads the parts of each URL against it:
1. The first segment of the path is the name of the controller.
1. The second segment is the name of the action.
1. An optional third segment is passed to the action as a parameter called `id`.

So if a request comes in at `/Walkers/Details/5`, the framework will look for a `Details` action in the `WalkersController` and call it, passing in `5` as the `id`. If a request comes in at `/Walkers/Index`, the framework will call the `Index` action in the `WalkersController`.

The pattern also sets some defaults. If the URL doesn't include an action, the framework will use `Index`, which means `/Walkers` would still call the `Index` action in the `WalkersController`. If the URL doesn't include a controller either, like the bare `/` you landed on when the app started, the framework assumes the `Home` controller and the `Index` action. You are welcome to change these defaults.

> :bulb: Your app runs on whatever port is listed in `Properties/launchSettings.json`, which was chosen at random when the project was created. Throughout this book, URLs are written as just the path, like `/Walkers/Index`. Add that to the end of the address your app is running on.

## Step 2: The controller
Open `Controllers/HomeController.cs`:
> HomeController.cs
``` csharp
public class HomeController : Controller
{
    public IActionResult Index()
    {
        return View();
    }

    public IActionResult Privacy()
    {
        return View();
    }

    // ...
}
```
There are two things to notice here.

1. In Bianca's Bike Shop, your [controllers](../../book-4-controllers/chapters/biancas-02-tour.md#whats-a-controller) inherited `ControllerBase`. MVC controllers inherit `Controller` instead. `Controller` itself inherits `ControllerBase`, so everything you've already used (like `NotFound()`) is still there, and it adds the methods a controller needs to work with views.
1. The most important of those methods is `View()`. Instead of `Ok()` sending data back as JSON, `View()` finds a view, renders it into HTML, and sends that HTML back as the response.

How does `View()` know _which_ view to render? By convention. It looks in the `Views` folder for a folder named after the controller (`Home`), and a file in that folder named after the action (`Index`). So the `Index` action in the `HomeController` renders `Views/Home/Index.cshtml`, and the `Privacy` action renders `Views/Home/Privacy.cshtml`. Open the `Views` folder and you'll find both of them right where `View()` expects them to be.

## Step 3: The view
Open `Views/Home/Index.cshtml`:
> Index.cshtml
``` html+razor
@{
    ViewData["Title"] = "Home Page";
}

<div class="text-center">
    <h1 class="display-4">Welcome</h1>
    <p>Learn about <a href="https://learn.microsoft.com/aspnet/core">building Web apps with ASP.NET Core</a>.</p>
</div>
```
Views are HTML templates that let you use code to change the final HTML output with data. You are already familiar with one templating syntax: JSX! JSX lets you fill HTML templates with dynamically generated elements and data in something that _looks_ a lot like HTML.

MVC has its own syntax for doing this with C#, called _Razor_. That's why this file isn't an `.html` file, it's a `.cshtml` file. With Razor we can write a mix of C# and HTML. Any C# code that we want evaluated starts with the `@` symbol. In this view, the `@{ }` block at the top runs some C# that sets the page's title. Everything else is plain HTML, for now. Starting in the next exercise, you'll pass data from a controller into a view, and use Razor to build HTML out of it.

## Step 4: The layout
`Index.cshtml` doesn't have an `<html>`, `<head>`, or `<body>` tag, and it doesn't have the navigation bar you saw at the top of the page. Those come from a _layout_. Open `Views/_ViewStart.cshtml`:
``` html+razor
@{
    Layout = "_Layout";
}
```
This file runs before every view, and tells each one to use the layout called `_Layout`. Now open `Views/Shared/_Layout.cshtml`. This is the HTML shell that wraps every page in the app. Here are the most important parts, with a lot of the markup left out:
> _Layout.cshtml
``` html+razor
<!DOCTYPE html>
<html lang="en">
<head>
    <title>@ViewData["Title"] - DeShawnsRazor</title>
    <!-- stylesheets -->
</head>
<body>
    <header>
        <nav>
            <a class="navbar-brand" asp-area="" asp-controller="Home" asp-action="Index">DeShawnsRazor</a>
            <!-- ... -->
            <a class="nav-link text-dark" asp-area="" asp-controller="Home" asp-action="Privacy">Privacy</a>
        </nav>
    </header>
    <div class="container">
        <main role="main" class="pb-3">
            @RenderBody()
        </main>
    </div>
    <!-- footer and scripts -->
</body>
</html>
```
1. `@RenderBody()` is where the view's HTML goes. When the `Index` action renders `Index.cshtml`, its HTML is dropped into the layout at this spot, and the whole thing is sent back to the browser as one page.
1. `@ViewData["Title"]` is the same `ViewData["Title"]` that `Index.cshtml` set at the top of the file. Each view can set its own title, and the layout puts it in the browser tab.
1. The links in the navigation bar don't have an `href`. Instead, they have `asp-controller` and `asp-action` attributes, which tell ASP.NET which controller and action the link should go to. ASP.NET uses them to generate the `href` when the page is rendered. Check the page source in your browser again, and you'll see that the Privacy link became `<a class="nav-link text-dark" href="/Home/Privacy">Privacy</a>`.

Make the app DeShawn's own: change the two places that say `DeShawnsRazor` in `_Layout.cshtml` to `DeShawn's Dog Walking`, and change the `<h1>` in `Index.cshtml` to say `Welcome to DeShawn's`. Restart the app to see your changes.

## Routing and HTTP requests
The framework uses more than just the path of a URL to decide which action to call. Here are the relevant parts of an HTTP request:

### Verb
**NOTE:** The actual term for this is "method", but we use that word enough already.

An HTTP request will have a verb like `GET`, `POST`, `PUT`, or `DELETE`. We can use different verbs at the same URL. For instance, we can make a `GET` request to `/Owners/Create`, and also a `POST` request to that same URL. You'll see why that's useful when you start building forms.

### URL
The URL `/Owners/Create` tips the framework off to look for an `OwnersController`, and specifically a `Create` action.

URLs can also carry **route parameters**. These are parts of the URL that typically hold things like IDs. If a request comes in at `/Owners/Details/81`, the `81` part of that URL is a route parameter. The framework will look for a `Details` action in the `OwnersController` and call it, passing in `81` as the parameter.

### Body
`POST` and `PUT` requests are likely to have a **body**. This is the thing we are actually submitting to the server. In your web APIs, the body was JSON. In an MVC app, the body is usually _form data_, the values a user typed into an HTML form. The framework knows how to take that raw form data and convert it to a C# object, like an `Owner`, so it can pass it as a parameter to an action that looks like this:
```csharp
[HttpPost]
public IActionResult Create(Owner owner)
{
    ...
}
```
